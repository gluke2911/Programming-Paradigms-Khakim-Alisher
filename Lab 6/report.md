## 1. Цель работы

Изучить применение общего интерфейса, наследования, полиморфизма и композиции, а также научиться заменять реализацию компонента без изменения основного сервиса.

## 2. Постановка задачи

Создать `ReportService`, который принимает заголовок и список записей и передаёт данные компоненту форматирования. Реализовать три взаимозаменяемых компонента: `TextRenderer`, `HtmlRenderer` и `MemoryRenderer`. Последний компонент должен сохранять результат в памяти для тестирования.

## 3. Архитектура

`Renderer` — абстрактный базовый класс с методом `render`. `TextRenderer`, `HtmlRenderer` и `MemoryRenderer` наследуются от него и реализуют один и тот же контракт. `ReportService` получает конкретный renderer через конструктор и делегирует ему форматирование.

Схема зависимостей:

```text
                 Renderer (ABC)
                /       |       \
       TextRenderer HtmlRenderer MemoryRenderer
                \       |       /
                 ReportService
```

## 4. Почему используются наследование и композиция

Наследование задаёт единый контракт для трёх способов вывода. Полиморфизм позволяет вызывать `render` одинаково, независимо от конкретной реализации. Композиция используется потому, что `ReportService` содержит ссылку на объект renderer и делегирует ему работу. Для замены формата не требуется менять код самого сервиса.

## 5. Описание классов

| Класс | Назначение |
|---|---|
| `Renderer` | Абстрактный контракт метода `render` |
| `TextRenderer` | Формирует обычный текст |
| `HtmlRenderer` | Формирует HTML и экранирует содержимое |
| `MemoryRenderer` | Сохраняет результат в памяти, считает вызовы |
| `ReportService` | Проверяет входные данные и вызывает renderer |

## 6. Проверки и обработка ошибок

Сервис отклоняет пустой заголовок, пустой список записей и пустые/некорректные записи. При передаче объекта, не реализующего `Renderer`, выбрасывается `TypeError`. Реализации renderer проверяют заголовок перед формированием результата. `HtmlRenderer` экранирует HTML-символы в заголовке и строках.

## 7. Тестирование

Автоматические тесты в `tests/test_reporting.py` проверяют:
- формирование текстового отчёта;
- формирование HTML-отчёта;
- экранирование HTML-разметки;
- сохранение результата в памяти;
- замену renderer без изменения сервиса;
- обработку пустого заголовка;
- обработку пустого списка записей;
- отклонение неподходящего компонента.

Запуск:

```bash

```

## 8. Контрольные вопросы

1. **Что такое наследование?** Механизм создания класса на основе другого класса.
2. **Что такое полиморфизм?** Возможность использовать объекты разных классов через общий интерфейс.
3. **Что такое интерфейс?** Контракт, определяющий доступные операции и их назначение.
4. **Для чего нужен ABC?** Для создания абстрактных базовых классов с обязательными методами.
5. **Что такое абстрактный метод?** Метод, который должен быть реализован конкретным подклассом.
6. **Что такое композиция?** Отношение, при котором один объект использует другой объект как часть своей реализации.
7. **Что такое внедрение зависимости?** Передача необходимого компонента извне, например через конструктор.
8. **Почему нужны разные renderer-классы?** Они позволяют формировать разные форматы с единым контрактом.
9. **Почему `MemoryRenderer` полезен в тестах?** Он хранит результат в памяти, не требуя файловой системы или внешнего сервиса.
10. **Зачем проверять входные данные?** Чтобы не формировать отчёт из некорректных данных.
11. **Почему HTML экранируется?** Чтобы строки с символами разметки отображались как текст, а не как HTML-код.
12. **Что означает взаимозаменяемость компонентов?** Основной сервис продолжает работать с другой реализацией, если она соблюдает тот же контракт.
